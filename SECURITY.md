# Security notes — RetinaGuard research prototype

## Current safeguards
- API routes are local-only unless `RG_API_TOKEN` is configured; when configured, all `/api/*` routes except the minimal health endpoint require a matching bearer token.
- Training paths are restricted to `RG_DATA_ROOT` after real-path resolution.
- Upload size and decoded image pixel limits are enforced; uploaded bytes must decode as an image.
- Checkpoints use `torch.load(..., weights_only=True)` and strict state-dictionary loading.
- Image payloads are excluded from the SQLite UI-state store; audit messages avoid filenames and raw image content.
- Database access has a timeout and WAL mode.

## Limitations / required before public deployment
- The token is a shared single-operator secret. The dashboard stores it in `sessionStorage`; this is not appropriate as a substitute for a proper identity/session system.
- Put the service behind HTTPS, a reverse proxy and SSO/OIDC or another reviewed authentication mechanism. Implement per-user and per-case authorization before storing multiple users' records.
- SQLite state is one shared UI state, not tenant-isolated patient/case storage. Do not use it for multi-user patient records.
- `/api/report` currently formats client-supplied result fields and does not prove the result was generated by the server. Do not use reports as authenticated clinical records.
- The exposed audit endpoint is read-only, but SQLite administrators can alter the underlying file. Use tamper-evident centralized logging for a production audit trail.
- Configure production storage, backups, retention/deletion, encryption at rest, secrets management, rate limits, monitoring and incident response.
- Review reverse-proxy request-body limits and timeouts as well as application limits.
- Do not log patient identifiers, uploaded images, API tokens or raw request bodies.

## Responsible-use statement
This software is a research prototype, not a medical device. Outputs must not be used for diagnosis or treatment decisions. Clinical use requires appropriate independent validation, expert review, risk management and applicable regulatory/ethics approvals.
